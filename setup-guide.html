    Das Repository automatisiert nur sichere und reproduzierbare Schritte. Apple-Logins, Lizenzen, biometrische Freigaben, private Schlüssel und macOS-Datenschutzrechte bleiben bewusst manuell. Wenn eine manuelle Aktion eine spätere Bootstrap-Stufe blockiert, hält der Bootstrap direkt dort an, wartet in einem interaktiven Terminal und prüft das Ergebnis vor dem Fortsetzen. Ohne interaktives Terminal beendet er sich mit Exit-Code 2 und nennt den erneut auszuführenden Befehl.

    Diese Schritte schaffen die minimale Umgebung, in der das Repository seinen eigenen Bootstrap übernehmen kann.

    Ab hier übernimmt das Repository. ./bootstrap.sh legt nur das Fundament und hört dann auf. Git-Identität, SSH-Schlüssel und die GitHub-Verbindung kommen danach von Hand, in der nächsten Phase, und erst dann startet das verwaltete Setup.     Den Mac initialisieren

    Automatisch 
    cd ~/github/phoenix-error/dotfiles
./bootstrap.sh

    ./bootstrap.sh installiert nur Xcode Command Line Tools, Homebrew und mise, verlinkt ~/.zprofile, ~/.zshrc und ~/.zsh_plugins.txt und hört dann auf. Danach neues Terminal öffnen, damit die Shell brew und mise findet.

    Nicht mit sudo starten. Das Skript lehnt einen Lauf als Root ab, weil der Homebrew-Installer das ebenfalls verweigert und alles Weitere dem eigenen Benutzer gehören muss. Es fragt das Passwort genau einmal ab, direkt bevor Homebrew /opt/homebrew anlegt.

    Diese Phase gehört zwischen ./bootstrap.sh und mise run setup. Git bringen bereits die Xcode Command Line Tools aus dem Preflight mit, es ist aber bewusst nicht Teil des Repos: ~/.gitconfig und ~/.ssh/config werden von Hand gesetzt, weil eine verwaltete Git-Konfiguration schon aktiv wäre, bevor der Schlüssel existiert, auf den sie sich bezieht. Wer das hier erledigt, läuft später ohne Unterbrechung durch das Gate des Setups. Es prüft genau eine Sache: dass ssh -T git@github.com erfolgreich authentifiziert. Private Schlüssel, Hosts und Logins bleiben ausschließlich lokal.

    Git-Identität von Hand setzen

    Bootstrap-Gate 
    git config --global user.name "Luca Becker"
git config --global user.email "luca.dev@outlook.de"
git config --global init.defaultBranch main

    Was die Befehle tun

    git config --global user.name "Luca Becker"
    Schreibt den Autornamen nach ~/.gitconfig. Er steht später in jedem Commit. --global heißt: gilt für alle Repositories dieses Benutzerkontos, nicht nur für das aktuelle.
    git config --global user.email "luca.dev@outlook.de"
    Setzt die Autoradresse. GitHub ordnet Commits über sie deinem Account zu.
    git config --global init.defaultBranch main
    Neu angelegte Repositories starten mit dem Branch main statt mit master.
    Diese Adresse ist in jedem öffentlichen Commit sichtbar und dauerhaft lesbar. Soll sie das nicht sein, stattdessen die GitHub-Noreply-Adresse 42442490+phoenix-error@users.noreply.github.com setzen und in den GitHub-Einstellungen Keep my email addresses private aktivieren.

    Sobald Homebrew Git installiert hat, pausiert der Bootstrap und wartet auf diese Schritte.

    ~/.ssh/config anlegen

    Manuell 
    mkdir -p ~/.ssh
chmod 700 ~/.ssh
cat > ~/.ssh/config <<'EOF'
Host github.com
  AddKeysToAgent yes
  UseKeychain yes
  IdentityFile ~/.ssh/id_ed25519
EOF
chmod 600 ~/.ssh/config

    Was die Befehle tun

    mkdir -p ~/.ssh
    Legt das SSH-Verzeichnis an. -p sorgt dafür, dass der Befehl nicht meckert, wenn es schon existiert.
    chmod 700 ~/.ssh
    Setzt die Rechte so, dass nur dein Benutzer hineinschauen darf. Sind sie weiter offen, verweigert SSH die Arbeit mit den Schlüsseln darin.
    cat > ~/.ssh/config <<'EOF' … EOF
    Schreibt alles zwischen den beiden EOF-Zeilen in die Datei. Die Anführungszeichen um 'EOF' verhindern, dass die Shell den Text vorher noch ersetzt.
    Host github.com
    Die eingerückten Zeilen darunter gelten nur für github.com.
    AddKeysToAgent yes
    Ein einmal entsperrter Schlüssel wandert automatisch in den laufenden ssh-agent, statt bei jeder Verbindung neu geladen zu werden.
    UseKeychain yes
    macOS legt die Passphrase in den Schlüsselbund. Ohne diese Zeile fragt SSH sie bei jeder Verbindung erneut ab.
    IdentityFile ~/.ssh/id_ed25519
    Benennt den Schlüssel, den SSH github.com anbietet, statt der Reihe nach alle vorhandenen durchzuprobieren.
    chmod 600 ~/.ssh/config
    Nur dein Benutzer darf die Datei lesen und schreiben.

    Das ist genau die Konfiguration, die auf dem aktuellen Mac läuft. Ein Host *-Block mit Keepalive-Optionen wäre möglich, ist hier aber nichts, was das Setup braucht.

    Ed25519-Schlüssel erzeugen und laden

    Manuell 
    ssh-keygen -t ed25519 -C "luca.dev@outlook.de"
ssh-add --apple-use-keychain ~/.ssh/id_ed25519
pbcopy < ~/.ssh/id_ed25519.pub
ls -l ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub
ssh-keygen -lf ~/.ssh/id_ed25519.pub

    Was die Befehle tun

    ssh-keygen -t ed25519 -C "luca.dev@outlook.de"
    Erzeugt das Schlüsselpaar: den privaten Schlüssel ~/.ssh/id_ed25519 und den öffentlichen ~/.ssh/id_ed25519.pub. -t ed25519 wählt das Verfahren, das GitHub empfiehlt. -C hängt einen Kommentar an den öffentlichen Schlüssel, an dem du ihn später in der GitHub-Liste wiedererkennst. Der Befehl fragt zuerst nach dem Speicherort, dort einfach Return für den Vorschlag, und danach zweimal nach der Passphrase.
    ssh-add --apple-use-keychain ~/.ssh/id_ed25519
    Lädt den privaten Schlüssel in den laufenden ssh-agent und legt die Passphrase in den macOS-Schlüsselbund, sodass du sie nicht wieder eintippen musst.
    pbcopy < ~/.ssh/id_ed25519.pub
    pbcopy ist die Zwischenablage von macOS, < schiebt ihr den Inhalt der Datei hinein. Danach hängt der öffentliche Schlüssel an der Zwischenablage und kann bei GitHub eingefügt werden.
    ls -l ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub
    ls listet Dateien auf, -l tut das im langen Format mit Rechten, Besitzer, Größe und Datum. Hier ist es reine Kontrolle: beide Dateien müssen existieren, und links soll -rw------- für den privaten und -rw-r--r-- für den öffentlichen Schlüssel stehen. Der private Schlüssel darf für niemanden außer dich lesbar sein, sonst weigert sich SSH, ihn zu benutzen.
    ssh-keygen -lf ~/.ssh/id_ed25519.pub
    Derselbe Befehl wie oben, aber im Anzeigemodus: -l heißt „zeig mir den Fingerprint“, -f benennt die Datei dazu. Der Fingerprint ist die kurze Prüfsumme des Schlüssels. GitHub zeigt sie neben dem hinterlegten Schlüssel an, sodass du beide vergleichen kannst.
    Nur ~/.ssh/id_ed25519.pub darf geteilt werden. ~/.ssh/id_ed25519 ist der private Schlüssel und bleibt auf dem Mac.

    Public Key bei GitHub als Authentication Key hinterlegen

    Manuell

    Den kopierten Schlüssel unter GitHub SSH and GPG keys als Authentication Key hinzufügen. Danach den dort angezeigten Fingerprint mit der Ausgabe von ssh-keygen -lf vergleichen.

    GitHub-SSH-Verbindung prüfen und das Gate schließen

    Bootstrap-Gate 
    ssh -T git@github.com

    Was der Befehl tut

    ssh -T git@github.com
    Baut eine SSH-Verbindung zu GitHub auf, um zu sehen, ob der Schlüssel akzeptiert wird. -T verlangt dabei kein Terminal, denn GitHub gibt keine Shell heraus, sondern antwortet nur mit einer Begrüßung und beendet die Verbindung wieder. Beim ersten Mal fragt SSH zusätzlich, ob der Host bekannt ist, und zeigt dessen Fingerprint.

    Den angezeigten Host-Fingerprint mit GitHubs veröffentlichten Fingerprints vergleichen und erst dann yes tippen. Erst nach successfully authenticated im Bootstrap-Terminal Return drücken. Das Gate prüft genau diese Verbindung und fragt so lange erneut, bis sie steht.

    Git LFS einmal pro Benutzerkonto aktivieren

    Einmalig 
    git lfs install

    Was der Befehl tut

    git lfs install
    Trägt die filter "lfs"-Sektion in ~/.gitconfig ein. Sie sagt Git, dass es LFS-Dateien beim Auschecken durch das echte Original und beim Committen wieder durch einen Zeiger ersetzen soll.

    Homebrew installiert über das Brewfile nur das Programm git-lfs. Dieser Befehl installiert nichts nach, er verbindet Git einmal pro Benutzerkonto damit. Ohne ihn liegen in einem LFS-Repository nur kleine Textdateien mit Zeigern statt der eigentlichen Inhalte. Ob er schon gelaufen ist, zeigt git config --global --get-regexp filter.lfs.

    Commits mit dem SSH-Schlüssel signieren

    Optional

    Das ist der Weg, den GitHub für ein bestehendes SSH-Setup dokumentiert: derselbe Ed25519-Schlüssel signiert, es kommt kein zweiter Schlüsseltyp und keine GPG-Verwaltung dazu. Alles hier ist freiwillig. 

    git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true

    Was die Befehle tun

    git config --global gpg.format ssh
    Stellt Git von GPG auf SSH als Signaturverfahren um.
    git config --global user.signingkey ~/.ssh/id_ed25519.pub
    Benennt den öffentlichen Schlüssel, dessen privates Gegenstück signiert. Es ist derselbe Schlüssel wie für die Anmeldung.
    git config --global commit.gpgsign true
    Signiert ab jetzt jeden Commit automatisch. Der Name der Option stammt noch aus der GPG-Zeit und gilt trotzdem für SSH-Signaturen.
    git config --global tag.gpgsign true
    Dasselbe für annotierte Tags.

    Danach denselben öffentlichen Schlüssel ein zweites Mal unter GitHub SSH and GPG keys hinterlegen, diesmal als Signing Key. Ein Eintrag als Authentication Key allein reicht nicht; ohne den zweiten Eintrag bleiben die Commits auf GitHub unverifiziert.

    Optional zusätzlich, damit auch lokal git log --show-signature eine gültige Signatur meldet statt nur „no signature“: 

    mkdir -p ~/.config/git
printf '%s %s\n' "luca.dev@outlook.de" "$(cat ~/.ssh/id_ed25519.pub)" > ~/.config/git/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.config/git/allowed_signers

    Was die Befehle tun

    mkdir -p ~/.config/git
    Legt das Verzeichnis an, falls es noch nicht existiert.
    printf '%s %s\n' "…" "$(cat ~/.ssh/id_ed25519.pub)" > …
    Schreibt eine Zeile aus deiner Adresse und dem öffentlichen Schlüssel in die Datei. $(cat …) setzt den Dateiinhalt an dieser Stelle ein, > leitet das Ergebnis in die Zieldatei um.
    git config --global gpg.ssh.allowedSignersFile …
    Sagt Git, welche Schlüssel als vertrauenswürdig gelten. Ohne diese Datei kennt Git lokal niemanden, dem es die Signatur zuordnen könnte, obwohl GitHub den Commit als Verified anzeigt.
    Das Setup selbst hängt an keiner Stelle daran. GitHub nimmt unsignierte Pushes an, und der einzige Gewinn ist das Verified-Abzeichen. Der Setup Doctor prüft Signaturen deshalb bewusst nicht.

    GitHub CLI später anmelden, wenn nötig

    Optional 
    gh auth login --hostname github.com --git-protocol ssh --web
gh auth status

    Was die Befehle tun

    gh auth login --hostname github.com --git-protocol ssh --web
    Meldet die GitHub CLI an. --git-protocol ssh lässt sie den eben eingerichteten Schlüssel statt HTTPS-Tokens verwenden, --web erledigt die Anmeldung im Browser.
    gh auth status
    Zeigt, als wer die CLI angemeldet ist und welches Protokoll sie nutzt.

    Nicht Teil des Bootstrap-Gates. Erst ausführen, wenn ein Workflow gh braucht.

    Git und GitHub stehen jetzt, also läuft das erste Gate ohne Pause durch. Der Lauf ist idempotent und darf nach einem behobenen Fehler erneut gestartet werden. Er hält danach noch an zwei Stellen an und wartet auf dich: die Anmeldung der Coding Agents und der Mac App Store. Diese beiden Pausen sind die nächsten beiden Phasen, in genau der Reihenfolge, in der sie im Terminal erscheinen.

    Das verwaltete Setup starten

    Automatisch 
    mise run setup

    Der Task aktualisiert mise und übergibt dann an mise bootstrap. Die Stufen laufen in dieser Reihenfolge: Homebrew-Pakete, das Gate für Git und SSH, die Rückfrage zu bereits vorhandenen Dotfiles, Dotfile-Symlinks, bestätigte macOS-Defaults, Runtimes, globale CLIs, Pause für die Coding-Agent-Anmeldungen, Oh-My-Pi-Settings, Composio-CLI, die Herdr-Agent-Integrationen, Pause für den Mac App Store, den täglichen Tool-Updater, den delegierten ssh-agent, den abendlichen omp-Sync und zum Schluss der Setup Doctor. Editor-Extensions und Direktdownload-Apps gehören nicht dazu.

    Hat eine App ihre Konfiguration schon selbst geschrieben, etwa ~/.claude/settings.json beim ersten Start von Claude Code, fragt der Lauf vor der Dotfile-Stufe nach. Ein y verschiebt die betroffenen Dateien mit Zeitstempel zur Seite und verlinkt danach die verwaltete Fassung, alles andere hält das Setup an. Gelöscht wird nichts.

    Meldet ./bootstrap.sh, dass die Shell-Konfiguration nicht verlinkt werden konnte, liegen dort schon handgeschriebene Dateien. Dann stattdessen ~/.local/bin/mise run setup aufrufen.

    Derselbe Befehl ist auch der Wiederholungsbefehl. Der Lauf ist idempotent und wird nach jeder behobenen Voraussetzung einfach erneut gestartet. Der Repository-Task heißt bewusst setup. Ein Task namens bootstrap würde von mise bootstrap selbst noch einmal aufgerufen und den ganzen Ablauf wiederholen.

    Der Lauf hält hier zum ersten Mal an, direkt vor den Herdr-Integrationen. Herdr kann einen Agent nur einhängen, wenn dieser einmal gestartet und angemeldet war. Auf einem frischen Mac existieren die Agents vorher gar nicht, Homebrew hat sie erst in diesem Lauf installiert. Deshalb ist die Anmeldung genau hier fällig und nicht früher.

    Alle sechs Coding Agents anmelden

    Login

    Das Setup wartet in seinem Fenster. Die Anmeldungen in einem zweiten Terminal erledigen, danach im Setup-Fenster mit Return bestätigen. Das Gate prüft das Ergebnis und fragt so lange erneut, bis alle sechs bereit sind. 

    claude          # danach /login
codex login
cursor-agent login

opencode auth login

    Ohne interaktives Terminal beendet sich das Gate mit Exit-Code 2 und nennt mise run setup als erneut auszuführenden Befehl. Einzeln nachholen lässt es sich mit mise run agents:login, gefolgt von mise run agents:herdr.

    Die letzte Pause vor dem Doctor. mas kann nur Apps installieren, die der verwendete Apple Account bereits einmal beansprucht hat. Passwörter und Apple-Anmeldestatus bleiben außerhalb des Repos.

    Cursor-Extensions optional von VS Code spiegeln

    Optional

    Cursor hat kein Microsoft Settings Sync. Wenn Cursor denselben Extension-Satz wie VS Code bekommen soll, einen Claude Agent mit dem Prompt unten spawnen. Er installiert alles, was Cursor laden kann, und überspringt IDs, die nur im Visual Studio Marketplace existieren, zum Beispiel Modernized. 

    Mirror my currently installed VS Code extensions into Cursor.

1. Run `code --list-extensions` and capture every installed extension ID.
2. For each ID, try `cursor --install-extension <id>`.
3. Skip extensions Cursor cannot install. Known cases:
   - `sukarth.vscode-modernized` (Visual Studio Marketplace only)
   - `ms-python.vscode-pylance` (Microsoft license; install `anysphere.cursorpyright` instead)
4. If VS Code has Pylance, ensure Cursor has `anysphere.cursorpyright`.
5. Report three lists: installed, already present, and failed with the exact error.

Do not change VS Code. Do not edit settings.json. Only install Cursor extensions.

    Globale Agent-Skills von Hand installieren

    Manuell

    Das Setup installiert keine Skills. Skill-Quellen werden umbenannt, geteilt und eingestellt, und zwar deutlich schneller als der Rest des Inventars. Ein veralteter Eintrag würde den ganzen Setup-Lauf scheitern lassen, ohne dass ein frischer Mac dadurch etwas gewinnt. Deshalb bleibt dieser Schritt bewusst Handarbeit.

    Immer bunx, nie npx. Die vier Agent-Ziele sind claude-code, codex, cursor und opencode. Jede Installation legt die kanonische Kopie in ~/.agents/skills ab und verlinkt die Agent-Verzeichnisse per Symlink darauf. Oh My Pi liest das kanonische Verzeichnis direkt und braucht deshalb kein eigenes Ziel. 

    bunx skills add mattpocock/skills \
  --agent claude-code --agent codex --agent cursor --agent opencode \
  --global

    Der Befehl öffnet die interaktive Auswahl von mattpocock/skills. Ohne --agent-Flags öffnet die Agent-Auswahl mit der zuletzt benutzten Auswahl vorbelegt und fragt danach nach Projekt oder global; Symlinks sind der Standard-Installationsmodus. Für eine nicht-interaktive Installation eines festen Satzes stattdessen --yes und ein oder mehrere --skill <name> anhängen. Dieselbe Form funktioniert mit jeder anderen Quelle: bunx skills add <owner/repo>.

    Drei Namen kommen über mehr als einen Kanal, jeweils mit anderem Verhalten dahinter: code-review gibt es als Skill und als Plugin, Library-Dokumentation deckt die verwaltete ctx7-Rule und das context7-Plugin ab, und Browser-Steuerung deckt die Shared-Core-CLI chrome-devtools-axi und die agent-browser-Formula ab. Die Plugins aus home/.claude/settings.json bringen ihre eigenen Skills mit.
